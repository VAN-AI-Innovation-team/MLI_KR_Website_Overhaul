# MLI 데이터 구조와 구현 규칙

## 저장소를 나누는 이유

`mli-ops`는 업무용 원본 DB입니다. 회원 식별정보, 상담 신청, 게시물 초안, 숨김·삭제 원문, 검수 기록을 보관합니다. `mli-content`는 공개할 필드만 추린 복사본과 승인된 AI 자료를 보관합니다.

공개 조회용 코드에는 `CONTENT_DB`만 주고, 관리자·회원·접수 코드는 `OPS_DB`에 접근하도록 이후 API를 구성합니다. 현재 상태 확인 Worker만 연결 확인을 위해 두 바인딩을 사용합니다. DB를 둘로 나눈 것 자체가 API의 인증·권한 검사를 대신하지는 않습니다.

회원 글과 공식 글의 원본도 `mli-ops`에 둡니다. 작성자 외래 키를 같은 DB 안에서 유지하고, 숨김 글이나 검토 중인 번역본이 공개 조회에 섞이지 않게 하기 위해서입니다. 공개 복사본에는 닉네임과 본문 등 공개 필드만 저장하고 이메일·Google subject·관리자 메모는 넣지 않습니다. 본문에 사용자가 쓴 개인정보가 있는지는 별도로 검사해야 합니다.

## 업무용 테이블 15개

| 분류 | 테이블 | 저장 내용과 관계 |
| --- | --- | --- |
| 회원 | `users` | 닉네임, 상태, 언어, 이용약관·개인정보 동의 버전과 시각 |
| 인증 | `auth_identities` | 회원과 Google 고유 subject 연결. 이메일을 회원 식별 키로 사용하지 않음 |
| 운영자 | `admin_memberships` | 허용된 회원의 역할과 활성 여부 |
| 세션 | `sessions` | 토큰의 SHA-256 해시, 회원, 종류, 발급·활동·만료·폐기 시각 |
| 상담 | `consultations` | 신청 원문, 동의, 희망 일정, 상태, 담당자, 내부 메모 |
| 문의 | `inquiries` | 일반·언론·연구·협업·오류 문의와 처리 정보 |
| 감사 | `audit_events` | 작업자, 대상, 행동, 상태 전후, 시각, 요청 식별자 |
| 게시물 | `posts` | 작성자, 게시판 종류, 공개 상태, slug, 전체 버전 |
| 번역 | `post_translations` | 게시물별 언어의 제목·요약·본문, 검수·버전 정보 |
| 수정 이력 | `post_revisions` | 언어별 과거 버전, 내용, 편집자 |
| 댓글 | `comments` | 원글, 작성자, 본문, 공개·숨김·삭제 상태 |
| 신고 | `reports` | 신고자와 대상 글 또는 댓글, 사유, 처리 상태 |
| 관리 조치 | `moderation_actions` | 운영자의 숨김·복원·삭제와 사유, 중복 방지 키 |
| AI 검수 원본 | `knowledge_documents` | 자료 출처, 본문, 허용 주장, 권리·검수 상태 |
| 발행 작업 | `publication_jobs` | 공개 복사본 동기화·제거 작업, 대상 버전, 재시도 상태 |

## 공개용 테이블 6개와 조회 뷰 2개

| 테이블 또는 뷰 | 용도 |
| --- | --- |
| `published_posts` | 발행된 게시물의 유형, 공개 작성자명, URL 식별자, 버전 |
| `published_post_translations` | 공개 가능한 언어별 제목·요약·본문 |
| `published_comments` | 공개 댓글. 원글의 공개 복사본을 삭제하면 함께 삭제 |
| `sources` | AI 자료의 원문 URL, 발행 주체, 유형, 현재 버전 |
| `knowledge_chunks` | 승인 증빙이 있는 자료 조각, 언어, 원문 위치, 유효기간 |
| `route_registry` | 실제 사이트 경로, 언어, 설명, 활성 여부, 필요한 권한 |
| `searchable_knowledge` 뷰 | 활성 상태이며 유효하고 현재 출처 버전과 일치하는 AI 자료만 조회 |
| `public_routes` 뷰 | 활성 상태의 공개 경로만 조회 |

공개 DB에는 상담·회원·세션 테이블이 없습니다. 초기 데이터나 가짜 운영자는 넣지 않았습니다. 실제 페이지를 구현하고 확인하기 전까지 안내 경로도 등록하지 않습니다.

## 핵심 관계

| 관계 | 의미 |
| --- | --- |
| `auth_identities.user_id → users.id` | Google 계정은 존재하는 회원과 연결 |
| `posts.author_id → users.id` | 글 작성자를 보존. 탈퇴 처리는 상태 변경과 개인정보 익명화 정책으로 구현 |
| `comments.post_id → posts.id` | 댓글의 원글이 존재해야 함 |
| `consultations.assigned_admin_id → admin_memberships.user_id` | 상담을 일반 회원에게 임의 배정할 수 없음 |
| `post_translations(post_id, locale)` | 같은 글의 언어별 버전은 하나씩 존재 |
| `knowledge_chunks.source_id → sources.id` | 모든 AI 자료 조각에 원문 출처가 존재 |

서로 다른 DB 사이에는 외래 키를 설정하지 않습니다. 공개 테이블의 `id`와 `source_version`은 원본 ID·버전의 복사값입니다. 동기화 서비스가 원본 상태를 검증해야 합니다.

## 상담 한 건의 데이터 흐름

아래는 다음 단계에서 구현할 API의 처리 순서입니다. 현재 1단계에는 저장 구조와 제약 조건까지만 구현되어 있습니다.

1. 서버가 입력 형식·길이·동의·Turnstile·요청 속도를 확인합니다.
2. 서버가 동의 버전과 UTC 접수시각을 결정합니다. 브라우저가 전달한 동의 버전을 무조건 신뢰하지 않습니다.
3. 클라이언트의 임의 요청 키와 서버에서 계산한 정규화 요청 해시를 비교합니다.
4. 새 요청이면 상담과 접수 감사 이벤트를 같은 `OPS_DB.batch()`로 저장합니다.
5. 같은 키·같은 내용이면 기존 접수번호를 반환하고, 같은 키·다른 내용이면 충돌 응답을 반환합니다. UNIQUE 제약만으로 이 응답 동작이 자동 구현되지는 않습니다.
6. 저장 성공 후에만 접수번호를 반환합니다. 실패하면 접수 완료나 예약 확정을 표시하지 않습니다.

`receipt_number`와 `idempotency_key`는 각 접수 테이블 내에서 고유합니다. 두 종류의 번호가 구분되도록 상담은 `C`, 일반 문의는 `I` 등의 접두어를 서버에서 붙입니다. 식별자나 접수번호만으로 개인정보 조회 권한을 주지 않습니다.

상담 상태의 저장값은 다음과 같습니다. 상태 간 전이 권한과 허용 순서는 이후 API가 검사해야 하며, DB는 정의된 상태값과 확정 일정의 존재를 검사합니다.

| 저장값 | 화면 표시 |
| --- | --- |
| `new` | 신규 |
| `reviewing` | 검토 중 |
| `needs_info` | 추가 정보 요청 |
| `proposed` | 일정 제안 |
| `confirmed` | 확정 |
| `completed` | 완료 |
| `cancelled` | 취소 |

관리자가 수정할 때 `WHERE id = ? AND version = ?`로 현재 버전을 확인하고 성공 시 버전을 올립니다. 다른 운영자가 먼저 바꿨다면 충돌을 알려 최신 데이터를 다시 읽습니다. 상담 상태 변경과 감사 이벤트도 같은 DB 배치에서 저장해야 합니다.

## 발행과 숨김의 처리 원칙

일반 게시물의 웹 발행과 AI 사용 승인은 별도 과정입니다. 회원 글·댓글을 자동으로 AI 지식에 넣지 않습니다. `knowledge_documents`는 권리 확인과 운영자 검수가 끝나야 승인 상태로 저장됩니다.

두 DB의 쓰기를 하나의 원자적 트랜잭션으로 묶을 수 없으므로 `publication_jobs`를 둡니다. 이후 발행 서비스는 원본 변경과 발행 작업을 하나의 `OPS_DB.batch()`로 저장하고, 공개 DB 반영에 실패하면 재시도합니다. 오래된 작업이 최신 내용을 덮어쓰지 않도록 원본의 현재 버전을 다시 읽고 `source_version`을 검사해야 합니다. 같은 대상·같은 버전의 작업은 중복 저장할 수 없습니다.

숨김·삭제·승인 철회는 공개 복사본과 검색·AI 색인·캐시를 제거한 것을 확인하기 전까지 완료로 응답하지 않아야 합니다. 공개 DB 반영이 지연되면 처리 중 또는 실패로 표시하고, 제거 실패를 성공처럼 처리하지 않습니다. 이 발행 처리기는 아직 구현하지 않았습니다.

`post_revisions`는 이력 저장용 테이블입니다. 이력을 자동으로 쌓는 트리거는 없으므로 이후 편집 API가 현재 버전 저장과 새 버전 갱신을 같은 배치로 처리해야 합니다. 회원 원문에는 관리자 검수 없는 공개를 허용할지 별도 정책을 적용하고, 공식 공지·보도자료에는 번역 승인과 발행 권한 검사를 적용합니다.

## 기본 자료형과 보안 경계

- ID는 서버에서 생성하는 무작위 UUID를 사용하도록 설계했습니다. DB는 TEXT로 저장하며 UUID 형식 검사는 이후 서버에서 수행합니다.
- 시간은 UTC Unix 초 정수입니다. 화면은 `preferred_timezone`을 기준으로 표시하고, 희망 일정과 `confirmed_time`은 별개로 취급합니다.
- `preferred_language`와 번역 언어는 `ko`, `en`, `zh-CN`, `es`, `fr`, `ja`로 제한했습니다. 원천 자료의 원문 언어는 더 넓을 수 있습니다.
- `token_hash`에는 임의로 생성한 충분히 긴 세션 토큰의 SHA-256 해시만 저장합니다. 원본 토큰은 HttpOnly·Secure 쿠키로 전달하는 다음 단계에서 구현합니다. Google 토큰이나 관리자 코드는 저장하지 않습니다.
- 운영자 가입 여부만으로 인증이 완료되지 않습니다. Google 검증, 추가 코드, 세션 만료, 계정 활성 여부, 역할, 소유권, CSRF·Origin 검사는 이후 모든 관련 API에서 수행해야 합니다.
- `CHECK`와 외래 키는 데이터 무결성을 검사합니다. 이메일의 정확한 형식, URL 안전성·정규화, XSS 방지 HTML 정화, 파일 검사는 서버에서 추가로 수행합니다. 경로 DB 검사는 기본적인 외부 URL 차단이며 전체 URL 검증기를 대신하지 않습니다.
- `updated_at`은 자동 갱신되지 않습니다. 이후 수정 API가 서버 시각으로 갱신해야 합니다.
- 감사 로그는 이벤트 메타데이터를 기록하는 구조입니다. 자유 입력 사유에 개인정보를 적지 않도록 서버 검증·운영 절차를 적용하고, 상담 원문·연락처·토큰·전체 요청을 복제하지 않습니다. 현재 DB 제약이 로그의 불변성이나 전체 민감정보 차단을 보장하지는 않습니다.
- `retention_until`은 운영 정책 확정 전에는 NULL입니다. 법정 보유 기간을 임의로 가정하지 않았으며 삭제 스케줄러는 이후 구현합니다.
- 숨김·삭제 상태는 보존 정책에 따라 처리합니다. 실제 영구 파기 시 FK로 연결된 수정 이력·관리 조치의 보존·삭제 순서를 먼저 결정해야 합니다.

## 구조를 변경할 때

아직 적용하지 않은 새 SQL 파일을 추가합니다. 적용한 마이그레이션을 고쳐도 기존 DB에는 재적용되지 않습니다.

```powershell
npx.cmd wrangler d1 migrations create mli-ops add_consultation_field
npx.cmd wrangler d1 migrations create mli-content add_public_media
```

필요한 DB에만 새 마이그레이션을 만든 뒤 테스트와 로컬 적용을 거칩니다. D1은 기본적으로 외래 키를 검사하므로 제약을 비활성화하는 방식에 의존하지 않습니다.

참고: [D1 마이그레이션](https://developers.cloudflare.com/d1/reference/migrations/), [외래 키](https://developers.cloudflare.com/d1/sql-api/foreign-keys/).
